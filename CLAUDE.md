# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

capynote (renamed from StrikeNote on 2026-10-09 — the lowercase `strikenote` identifiers below — DB name/user, systemd service, `/etc/strikenote`, `/opt/strikenote`, localStorage keys, drag MIME types — were deliberately kept so an existing install keeps working; folder name `report_system`, UI title 報告筆記系統): a self-hosted, HackMD-style Markdown note app for pentest/exam reporting. It generates OSCP / OSEP / CPENT-LPT / VHL report templates and two structured Taiwanese "資安院" report modes, and exports paginated PDFs. UI strings and most comments are Traditional Chinese.

## Running

There is no build step, no linter, and no unit-test suite. The front-end is plain static files served by the Node server; a front-end change only needs a browser refresh. The server has exactly one npm dependency, `mysql2` (`npm ci`); the database is **MariaDB** (10.11+).

```
npm ci
node server/server.js                                            # npm start; http://localhost:8080
node server/tools/smoke.js                                       # npm run smoke; end-to-end API exercise against a SCRATCH server
node server/tools/migrate-sqlite-to-mariadb.js --sqlite data.db  # npm run migrate; one-shot import of a pre-MariaDB SQLite file (--dry-run first)
node server/tools/import-md.js --dir ./out --url https://…      # npm run import-md; batch-import a folder of Markdown, images and all (--dry-run, --help)
```

Requires Node 22+. Runtime settings are env vars only, read in `server/config.js`: `PORT`, `HOST`, `DB_HOST`/`DB_PORT`/`DB_SOCKET`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` (the server refuses to start without a password unless a socket is given), `REGISTER_MODE` (open|invite|closed, default invite) and `INVITE_CODE` — both only *starting* values: once an admin changes either in 帳號管理 the `settings` table wins (`server/settings.js`), so editing the env afterwards does nothing — `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `TRUST_PROXY`, `REQUIRE_HTTPS`, `SESSION_TTL_DAYS`, `MIN_PASSWORD_LENGTH`, `MAX_LOGIN_ATTEMPTS`/`LOGIN_LOCKOUT_MINUTES`, `MAX_BODY_BYTES`, `UPLOAD_MAX_BYTES` (default 1 GiB; the whole-file cap for chunked uploads, 0 turns them off), `STORAGE_WARN_MB`/`STORAGE_WARN_PCT`, `TRASH_KEEP_DAYS` (default 30), `LINK_PREVIEW` (default 1; 0 stops the server fetching pages for link preview cards). `deploy/env.example` lists them all with production values. Production is a Raspberry Pi / Debian host provisioned by `deploy/install.sh` (idempotent: re-running it is also the update path), with settings in `/etc/strikenote/env` and TLS terminated by cloudflared or a reverse proxy; see `deploy/README.md`. On first start with no admin, a random admin password is printed once to stdout; in invite mode with no code yet, a random invite code is generated, stored in `settings` and printed once — after that it is shown (and can be changed or regenerated) in 帳號管理, which is also where an admin switches between 邀請制 / 開放註冊 / 關閉註冊.

A local MariaDB for development, with the same settings production uses:

```
docker run -d --name strikenote-db -e MARIADB_ROOT_PASSWORD=root -e MARIADB_DATABASE=strikenote \
  -e MARIADB_USER=strikenote -e MARIADB_PASSWORD=dev -p 127.0.0.1:3307:3306 mariadb:10.11 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci --max-allowed-packet=64M
DB_PORT=3307 DB_PASSWORD=dev PORT=8090 REQUIRE_HTTPS=0 REGISTER_MODE=open node server/server.js
```

A scratch instance is a different `DB_NAME` (or a different container), never the production database. The schema is created and additively upgraded by `db.init()` on every start, so an empty database is all a scratch instance needs.

`smoke.js` is the closest thing to a test suite: one script run top to bottom (there is no way to run a single section), printing PASS/FAIL per check and exiting 1 on any failure. It targets `BASE_URL` (default `http://127.0.0.1:8090`), logs in as `ADMIN_USERNAME`/`ADMIN_PASSWORD` (default `admin` / `scratchpass123`) and self-registers a second user `bob` with an empty invite code, so start the scratch server with `ADMIN_PASSWORD=scratchpass123 REGISTER_MODE=open` on an empty database. Its body-limit check reads `MAX_BODY_BYTES`, so give both processes the same value. `--old` skips the MariaDB-only checks.

Cache busting: every `<script src="js/x.js?v=N">` and the `app.css?v=N` link in `index.html` carry a version query. Bump the number when you change that file. The server already sends `no-store` for its own `.html`/`.css`/`.js` (only `vendor/` is cacheable, for a day), so the bump is the second line of defence against a proxy or CDN edge in between that holds an old copy; keep doing it.

## HARD RULE: never touch real note data

The production MariaDB database, and the pre-migration SQLite file `server/data/data.db` (plus the `server/data-recovery*/` snapshots) still on this machine, hold the user's real exam reports, which are confidential graded evidence. Do not open, query, read, or write any of them, and do not drive the user's logged-in browser tab: on reload the app auto-opens the last note and any `input` event on `#editor` autosaves to the server within ~500 ms, which has already destroyed a real note once. To reproduce or verify anything, use synthetic data in a throwaway harness (a scratch `DB_NAME`/container as above, or serve the static files from another port with no backend, or call `MD.render(...)` / `PDF.showPreview(...)` directly). `server/tools/smoke.js` builds such a fixture; it must only ever be pointed at a scratch server. The migration tool is likewise only ever run by the user against the real file.

## Architecture

### Server (`server/`, one dependency: `mysql2`)

- `server.js` is the only HTTP entry: hand-rolled router for `/api/*`, static file serving from the repo root through an **allow-list** (`STATIC_ALLOW`: only `index.html`, `app.css`, `logo.png`, `favicon.*`, `js/*.js`, `vendor/**`; everything else — `.git/`, `docs/`, `*.md`, `server/` — is 404), security headers, HTTPS redirect behind a proxy, `/api/health` (DB ping, answered before the redirect so a local curl works), 413/400 for oversize/malformed bodies, `uncaughtException`/`unhandledRejection` → log and exit so the supervisor restarts it. It speaks plain HTTP only; TLS is the proxy's job. `server.keepAliveTimeout` (95 s) deliberately outlasts cloudflared's 90 s reuse of idle upstream connections: at Node's default 5 s the two crossed, and a POST sent down a socket Node was just closing came back as a 502 (the proxy only retries GETs by itself). With `TRUST_PROXY=1`, "secure" means `X-Forwarded-Proto: https` **or** Cloudflare's `CF-Visitor` says so, the client IP comes from `CF-Connecting-IP` then `X-Forwarded-For`, and HSTS is only sent on responses that were actually secure. Exactly one instance runs: presence/SSE and the login throttle are in-process.
- `db.js` owns the schema (users, sessions, folders, notes, images, shares, note_versions, book_versions, book_links, settings) and every prepared statement in the `q` object, on a `mysql2` pool. `q.<name>.get/all/run` are **async** (`run` resolves to `{insertId, affectedRows}`); `db.init()` creates the tables (`CREATE TABLE IF NOT EXISTS`, one statement per array element) and applies the additive `MIGRATIONS` list via `addColumnIfMissing` (information_schema, not try/catch). `tx(async fn)` checks out a connection, BEGINs, and binds it through `AsyncLocalStorage` so every `q.*` inside the callback runs on it; a nested `tx` joins the outer one. Deadlocks / lock-wait timeouts / a restarting MariaDB are "busy": retried a few times, then surfaced with `err.busy`, which the router maps to HTTP 503 + `Retry-After` and the client store retries. Two rules for `tx` callbacks: nothing that escapes the transaction (hub broadcasts, timers) may run inside — collect and fire after — and the body must be safe to run twice. Text ids/tokens are `utf8mb4_bin`; `username` is case-insensitive (`utf8mb4_unicode_ci`), so `Admin` and `admin` are one account. `LENGTH()` in the storage statements is bytes; the version/link lists use `CHAR_LENGTH()` because the UI shows characters.
- `api.js` holds all business logic. Authorization rule for the whole file: identity comes from the session, never the body. Note permission is `owner` | `edit` | `read` via `permFor()`: an explicit share row wins, otherwise the note's "general access" (`notes.access` = `restricted` | `site`, with `access_perm`) lets any signed-in user in. There is deliberately no anonymous or link-token access *to the API*: the only thing an account-less visitor can ever receive is a stored snapshot page at `/s/<token>` (e-book links and, since the user asked to "分享給沒有帳號的人", single-note public links — see those bullets). Folders are private and never shared; an image is readable by anyone who can read a note whose content contains `img:<id>` or `pdf:<id>`; admin endpoints (`/api/admin/users`, `/api/admin/storage`) return account metadata, counts and byte sizes only, never note text.
- **Areas (`notes.area` / `folders.area`, `server/api.js` `AREAS`/`normalizeArea`):** a note's or folder's home is `NULL` (一般 — the dashboard/sidebar tree exactly as before this existed) or one of `'course'` (課程筆記) / `'knowledge'` (知識區) / `'quick'` (隨筆) / `'novel'` (小說), set at creation — `updateNote`'s SQL has no `area` column, so a normal save can never change it, and `resolveArea()` refuses to create a note/folder whose `area` doesn't match the folder it's filed into (a folder's own area is likewise fixed, checked the same way on every move). Three of the four areas ride along in the *same* `GET /api/notes`/`GET /api/folders` response as general notes (cheap to expose, filtered client-side by `.area` — see the front-end bullet below); `'novel'` is the one excluded even from its own owner by the SQL itself (`notesOwned`/`foldersOf`: `area IS NULL OR area <> 'novel'`) until unlocked. **Moving a note between 所有筆記／課程筆記／知識區** (`PUT /api/notes/:id/area` → `moveNoteArea`, `MOVABLE_AREAS = [null, 'course', 'knowledge']`) is the one deliberate way area *does* change after creation — owner-only, validated exactly like `resolveArea` (the target folder, if given, must belong to the target area), and pointedly refuses `'novel'`/`'quick'` on either end: novel stays behind its gate with no back door, and quick notes have no folder concept to land in. It resets `position` to `NULL` (a manual-order slot from the old area's level means nothing in the new one). Reachable from three places that all funnel into the same `js/app.js` `moveNoteToArea()`/`doMoveNoteArea()` — the dashboard's "⋯" menu and the sidebar tree's right-click (both only ever show general notes, so the option is always offered there) and `js/areabrowser.js`'s own row action (wired through `areaOpts().onMoveArea`, offered only when `MOVABLE_AREAS` includes the note's current area) — picking a target area opens `showFolderPicker` scoped to that area's own folders (`o.folders` override), then `refreshViews()` picks the change up everywhere at once since every area's notes/folders are always freshly filtered from `state.notes`/`state.folders`, never cached per-view. **`permFor()` is the single choke point that makes 小說 real protection, not a client-side skin**: `if (note.area === 'novel' && !(owner && novelUnlocked(user))) return null` — the same pattern that already makes a trashed note invisible to every route (versions, images, PDF-via-read, sharing) without each of them special-casing it. `novelUnlocked(user)` checks `user.novelUnlockedAt` (attached onto the user object by `auth.userFromToken` from `sessions.novel_unlocked_at`) is set and fresher than `NOVEL_UNLOCK_TTL_MS` (1 hour). `POST /api/novel/unlock` (`server/auth.js` `unlockNovel`, called from `js/app.js` `promptNovelPassword()`) re-verifies the caller's *own current* password (`auth.verifyPassword`, sharing the login throttle keyed with a `'novel:'` prefix so a wrong novel-password attempt can't lock out real login) and stamps that session's row — **a wrong attempt must answer 403, never 401**: `js/store.js`'s `req()` treats any 401 as "session expired" and force-logs-out via `alert()`, which is the wrong response to a second-factor typo and was live in this codebase once before the fix. A novel note can never be shared or opened site-wide (`setAccess` refuses `area === 'novel'` outright); `js/app.js`'s own `novelIsUnlocked` flag is deliberately never persisted (in-memory only, so every fresh page load re-prompts even if the server-side unlock is still within its hour) — the UX is a per-visit gate, not a per-login-session one. `server/backup.js` round-trips `area` through export/import (`normalizeArea`, re-exported from `api.js`) and refuses to restore a novel note with `access: 'site'` even if the archive claims one.
- `updateNote` distinguishes text changes (bump `rev`, broadcast, touch `updated_at`) from bookkeeping changes (folder move, `meta` such as `pinned`), which are written without any of that. Do not reintroduce the old early return that compared only content and title: it silently dropped folder moves. Because the DB is async, two saves for one note can interleave, so every read-merge-write on a note (`updateNote`, `restoreVersion`, `restoreBookVersion`, `createVersion`) re-reads the row with `q.noteByIdForUpdate` **inside** its transaction and computes from that locked copy; the permission check on the plain read before it is only a pre-check. `restoreBookVersion` is one transaction for the whole book, locking chapters in manifest order. The admin "last admin" guards use `countAdminsLocked` inside the transaction for the same reason.
- Low-disk warning: `storageSummary()` uses `fs.statfs` on MariaDB's data directory (`SELECT @@datadir`, cached by `db.init()`, falling back up the path); thresholds are `STORAGE_WARN_MB` / `STORAGE_WARN_PCT`. The server logs it at start and hourly; admins get a banner from `Admin.checkStorage()` on login. `adminStorage()`'s `dbBytes` is InnoDB data+index size from `information_schema.TABLES`. Backups are `deploy/backup.sh` (`mariadb-dump --single-transaction`), not anything in the app.
- **System monitor (`server/sysmon.js`, `GET /api/admin/system` → `api.js:adminSystem`, 帳號選單 → 系統監控 in `js/admin.js` `showStorage()`):** the admin-only 儲存空間 dialog grew into a live monitor and was renamed. `sysmon.start()` (called from `server.js` after the storage check) samples once every 5 s — CPU from `os.cpus()` idle/total deltas (the first sample reads 量測中), memory from `/proc/meminfo` (`MemAvailable`, swap; falls back to `os.freemem()` off Linux), load average, SoC temperature from `/sys/class/thermal/thermal_zone0/temp` (absent → omitted, the UI hides the card), plus this process's `cpuUsage`/`memoryUsage` — and keeps `HISTORY` (120 samples, 10 min) for the sparklines. `snapshot(extra)` merges in `hub.stats()` (SSE connections, notes open, distinct users), `q.sessionStats` (live sessions / users), `q.countUsers` and the old `adminStorage()` — so the dialog's bottom section is still the per-account storage table, unchanged. It returns host metadata, counts and byte sizes only, never note text, and like every admin route answers 403 to non-admins (`smoke.js` has both checks). **Disk throughput** (asked for as 「系統監控要加上磁碟寫出入速度」): `diskTotals()` sums `/proc/diskstats` sectors read/written (×512) over whole devices only (`DISK_RE`: sda, nvme0n1, mmcblk0…, never partitions — they would double-count), `sample()` turns two readings into `diskIo = { read, write }` bytes/s and appends `rd`/`wr` to the history points; `snapshot().io` is `null` off Linux and the card then says so. The card's gauge and sparkline are scaled to the fastest moment in the ten-minute history, since there is no natural 100%. The dialog re-fetches every 5 s while open and stops on close (`renderSystem`/`gauge`/`sparkline`/`kv`/`pctClass` in `admin.js`; `.sys-*` in `app.css`). **It never grows past the viewport**: `.modal.sys-modal` is a flex column capped at `100dvh - 32px` and only `.storage-body` scrolls, so the title and 關閉 stay put — before, on a laptop-height window the dialog overflowed the overlay's flex centring and both ends were cut off with no way to scroll (user: 「不要上下卡住」). Nothing is persisted: history lives in the process and starts empty on each restart.
- **Backup and restore (`server/backup.js`, `server/zip.js`, `js/backup.js`; 帳號選單 → 備份與還原):** `GET /api/backup?scope=mine|site` streams a zip built by the dependency-free `ZipWriter` (whole entries, real sizes in every local header, UTF-8 names, zip64 only when needed) straight into the response with back-pressure, fetching one note / one image at a time so a big site is never in memory at once. The layout is readable without the app — `notes/<資料夾>/<標題>.md` (trashed under `_垃圾桶/`, site scope under `<username>/`), `files/<id>.<ext>`, `versions/<noteId>/<versionId>.md`, `books/<token>.html` — and the JSON indexes (`folders.json`, `notes.json`, `files.json`, `books.json`, plus `users.json` with scrypt hashes and `settings.json` for `site`) carry ids, timestamps, meta, access, shares and positions. Restore reads only the indexes and the paths they name (`findManifest` tolerates a re-zipped parent directory), so stray entries are ignored. **Restore keeps ids and is idempotent**: missing rows are recreated with their ids and timestamps (`insertNoteFull` etc.), existing rows owned by the caller are skipped unless `overwrite`, which snapshots the current text as a version labelled 還原備份前 first and broadcasts through the hub; an id owned by someone else is a conflict, skipped and reported, never taken over. A `mine` backup always restores into the caller's account; a `site` backup (admin only) maps owners by username, creates missing accounts with their old hashes and keeps existing ones — so the restoring admin's password never changes. Version ids are AUTO_INCREMENT and are remapped into book-version manifests; a book version whose chapters cannot all be resolved is skipped. Uploads come in chunks (`PUT /api/backup/upload/:id?offset=N`, each under `MAX_BODY_BYTES`, refused on an offset mismatch so a retried chunk cannot double-append) into `os.tmpdir()` up to `BACKUP_MAX_BYTES`, then `inspect` returns the manifest for the confirm step and `restore` runs as a background job the client polls — behind a tunnel one request can neither carry 100 MB nor stay open for minutes. One restore runs at a time; temp files and finished jobs are swept after an hour, and leftovers from a crashed process at start.
- **Trash (soft delete):** `DELETE /api/notes/:id` does not delete — it sets `notes.deleted_at` (ms epoch). `permFor()` treats a row with `deleted_at` as non-existent, so every normal route (read, save, versions, shares, image visibility, listings) 404s on a trashed note without each of them having to know; only `GET/DELETE /api/trash`, `DELETE /api/trash/:id` and `POST /api/notes/:id/restore` look at those rows, owner-only. Shares, versions and images stay attached, so restore is a one-column update; `q.restoreNote` also nulls a `folder_id` whose folder was deleted meanwhile, otherwise the note would come back invisible. Hard deletes (`q.deleteNote`, FK cascades) happen only on purge, empty-trash, or the hourly `purgeTrash` sweep in `server.js` after `TRASH_KEEP_DAYS`. The client side is a full page, not a dialog: `openTrash()` in `app.js` (the sidebar's 垃圾桶 row, or `#trash`) hides the other views and shows `#trash-wrap`, and `Trash.render(container, opts)` in `js/trash.js` draws a dashboard-style page into it (breadcrumb head, a separate section for notes within 3 days of purge, per-row and checkbox-batch restore/purge, search, 清空垃圾桶). `showEmpty`/`openNote`/`openBook` hide it again. Like the dashboard it keeps the sidebar drawer open (`openTrash` opens it, and the click-outside rule in `initSidebarDrawer` skips both views), and `refreshViews()` re-renders it while it is visible so a note deleted from the sidebar appears without a reload. `app.js`'s "delete" paths just call `Store.deleteNote` and re-word the confirm. Deleting a folder still deletes the folder row outright — only its notes go to the trash.
- `auth.js`: scrypt passwords, sessions stored as SHA-256 of a random token in an HttpOnly SameSite=Strict cookie `rn_session`, per-username+IP login throttling. CSRF is a custom `X-Requested-With` header check on non-GET requests.
- `hub.js`: in-memory Server-Sent Events fan-out per note id (`/api/notes/:id/events`) carrying `update`, `presence`, and `cursor` events. Nothing is persisted.
- **`js/merge.js` is the one merge, for both sides** (`server/merge.js` is a one-line `require('../js/merge.js')`; the file is a UMD wrapper — `module.exports` under Node, `window.Merge` in the browser). Client and server must resolve every conflict identically or two editors never converge; there used to be two hand-synced copies. `merge3(base, mine, theirs)` works in three levels, each only where the level above found both sides touching the same region: **lines** (`lineHunks`: LCS on the middle after trimming the common start/end — typing touches a few lines, so a 5000-line note merges in ~1.5 ms instead of an O(lines²) table under the row lock — then `slideHunks`, then `coarsenLines`, which joins line hunks separated only by one line or up to three blank/near-blank lines, because the LCS likes to pair some blank line with another and describe "edited these lines" as "deleted them, re-inserted edited copies further down", which duplicated or dropped the other person's edit of the same lines), then **tokens** (`tokenize`: ASCII words, runs of spaces, `\n`, and every other code point — CJK, punctuation, emoji — on its own; char-level LCS paired the letters of a new word with an old one next to it and cut both apart, which in a three-way merge interleaved two people's text), then **characters** inside the few words both sides changed (`mergeLetters`: "b"→"Xb" and "b"→"bY" is "XbY"). `slideHunks` moves every pure insertion/deletion to the position with the most natural boundaries on both sides (line break > space > punctuation, diff-match-patch style) so two people inserting at "the same place" really land on one spot, and joins same-side hunks it brings together. Conflicts: hunks that `overlaps()` (overlapping ranges, an insertion strictly inside the other's range, or two insertions at the same point — that last case must stay a conflict, see below) are grouped transitively by `combine`, whose output is checked for overlap and falls back to the old drop-theirs rule if it ever broke. At the character level an edit of the very same characters goes to mine — **unless one side only deleted there**, then both deletions stand and the other side's new text goes in (operation-based editors do the same with delete vs. retype: two people removing the same lines while one typed at their edge keep what was typed). **Same-spot insertions (`sameSpot`) keep both, mine first**, except: one side already contains the other's text → that side; a shared start/end with at least `SHARED` (20) non-space characters → the shared part once plus both differing middles (a short shared run like a space or "- " is not factored, or "the cat"/"the dog" would splice into "the catdog"); bigger than `BOTH_CHARS`/`BOTH_LINES` → mine wins; for characters, a part ending in `\n` goes first. Those containment and size rules are what keep the old failure from coming back: a save measured against a stale or empty `baseContent` "inserts" text the server already has at the same point, and blindly keeping both once took a note from ~15 KB to 1.5 MB under 50 concurrent saves (with `overlaps()` treating same-point insertions as conflicts at all, which must stay). `toText`/`fromText` hand a line region to the token merge with **every line carrying its own newline**, so "no lines" and "one empty line" stay different (joined plainly, two people deleting the same line left an empty line). `mapOffset(oldText, newText, offset)` maps a caret through a change the same way (by line; inside a changed line token by token, and letter by letter inside a changed word; text inserted exactly at the caret stays after it) — see the collaboration bullet. The scratchpad suite that covers all of this (fixed cases, random property checks, a full protocol simulation of 2–4 clients with out-of-order replies and SSE, an insert-only run where every typed token must survive exactly once, the stale-base snowball, and timing) is `merge-test.js`/`merge-debug.js`; `smoke.js` has API-level checks (same line → both kept, same spot → both kept, stale-base save → no duplication).

### Front-end (`index.html` + `js/` + `app.css`, vanilla JS)

Every module is an IIFE that publishes one global (`Icons`, `Store`, `Auth`, `MD`, `Editor`, `Templates`, `EditorHL`, `TableTool`, `OSCP`, `SecReport`, `SecEditor`, `PerfReport`, `Dashboard`, `Annotate`, `PDF`, `Search`, `Admin`, `Migrate`, `Merge`, `Book`, `MindMap`, `Versions`, `Trash`, `ImageLib`, `Graph`, `DrawIO`, `LineSync`, `App`). Load order in `index.html` matters because later scripts call earlier globals; `app.js` is last and orchestrates everything (tree, view modes, autosave, sharing UI, PDF button, paste/drop upload, book mode entry).

- **The markdown editor is always dark**, in both themes — it is a code surface, and only the preview follows the light/dark toggle. Its colours live in the `--ed-*` tokens defined once on `:root` with no `[data-theme="dark"]` overrides; every rule under `.edit-toolbar` / `.editor-area` / `.cm-*` / `#editor` must use those tokens, never `--bg` / `--text` / `--border`, or the editor will go light-on-dark.
- **The editor's syntax highlighting is a separate overlay (`edithl.js`) laid out independently of the textarea.** `#editor` is `color: transparent`; what you see is `.cm-lines` (one `.cm-row` per source line) drawn behind it, kept in step only by `translateY(-scrollTop)` and by both boxes having identical wrap width and identical row heights. Anything that makes a single `.cm-row` differ from the textarea's 31.5px line (e.g. a row with no line box — an empty `<span>` collapses to the 28px gutter — or a line that wraps at a different width) shifts every row below it, and the caret/selection visibly lands on the "wrong" line a few hundred lines down. Hence: blank lines always get a U+200B so they keep a line box, and `--sbw` is measured live from `ta.offsetWidth - ta.clientWidth` on every render (same trick as `syncMirrorStyle` in `app.js`). To check a note, compare `#editor.scrollHeight` with `.cm-lines`' height — they must agree to within 1px.
- **The app shell must never scroll; only the inner panes do.** `#app` is a fixed-height (`100vh`) flex column — `#topbar` (fixed 52px) then `#app-body` — and `html`, `body`, `#app` and `#app-body` are all `overflow: clip`, **and `body` is `position: relative`**. Both halves are load-bearing. On an element, `clip` (not `hidden`) means "not a scroll container", so a `scrollIntoView`/`focus()` skips `#app`/`#app-body` and walks up to the viewport — but `overflow: clip` on `html` is applied to the *viewport* as `hidden` (css-overflow-3), and `hidden` still allows programmatic scrolling. Measured in Chrome 152: with anything sticking out below the fold, `window.scrollTo` and a preview heading's `scrollIntoView({block:'start'})` (the TOC click in `app.js`) both moved `document.scrollingElement`, the latter by exactly the topbar height. So the real guarantee is that *nothing can ever extend past the viewport*: `body` is positioned so an absolutely-positioned body child is contained by `body`'s clip instead of escaping to the initial containing block and growing the viewport's scrollable overflow. That escape was the actual bug behind three fixes (`0bf3904`, `8a206d3`, this one): the caret-measuring mirror `<div>`s in `js/editor.js` (slash popup) and `js/table.js` (table toolbar) are appended to `body` once and cached, copy the textarea's `height`, and were `position: absolute` with no offsets — from the first `/` onward they sat just below `#app`, ~editor height tall, and the next TOC click scrolled the whole shell up 52px: topbar gone, `body`'s background as a strip under the statusbar (reads as "the footer got bigger"). They are `position: fixed; top:0; left:0` now. Rules: anything appended to `body` must be `position: fixed` (every overlay, popup and toast already is); to check a live page, `document.scrollingElement.scrollHeight` must equal `clientHeight`, and if it doesn't, list `document.body.children` for the one with a height below the fold. - **Editor/preview line sync (`linesync.js`):** click a line on either side and that line is underlined on *both* sides — the editor row and the matching preview text, image or code line. Deliberately a companion pass outside `markdown.js` — it never touches `MD.render()`, a renderer, or an extension, so it cannot affect PDF export, the published e-book, or search, none of which call it. It takes the note's top-level blocks from `marked.lexer()` — the same `marked` instance, so the callout/container/RISK/`[toc]` extensions are included and each token is exactly one rendered block — finds each token's `raw` in the source (after the same CRLF and leading-tab normalisation marked applies) for its line range, and pairs tokens with the already-rendered preview DOM by *position* per kind — the Nth heading token with the Nth outermost `<h1..h6>`, and so on — the same idea `app.js`'s own `editorBlocks()`/`previewBlocks()` use for the split-view scroll anchors. Do not go back to a hand-written block scanner: the first version had one, and every construct where it disagreed with marked (a `<br>` or other raw-HTML line, indented code, a setext heading, a lazy continuation line, text right after a table, a pipe-less table, a link definition) added a phantom paragraph, so every later paragraph underlined its neighbour — and a lone `| grep` line looped forever. Elements are matched *outermost*, not as direct children, because a raw-HTML wrapper (`<details>`, `<div align="center">`) can enclose markdown blocks; the blocks a raw `html` token produces itself are counted in a `<template>` and skipped. Paragraphs and list items get split further at each `<br>` (breaks:true's one-newline-one-`<br>` guarantee, plus one more per literal `<br>` typed on a line), and un-numbered code blocks at each newline inside their `<code>` (line-numbered code already has one `<li>` per line), into one `<span class="sync-ln" data-line0 data-line1">` per source line, reusing `markdown.js`'s `splitHighlightedLines` tag-stack trick (generalized from splitting on `\n` to splitting on `<br>`, and from `<span>`-only to any tag, with void elements like `<img>`/`<input>` excluded from the open-tag stack since they have no closing tag to balance). Blockquote/callout/RISK-finding/mindmap blocks — and a code block as a whole, for its fence lines — are tagged as ONE coarse range instead — not addressable line-by-line the way plain text is — and a list item's own text is refined the same way but a *nested* sub-list inside it is left completely untouched, falling back to the outer `<li>`'s own coarse range. Every tagged element carries `data-line0`/`data-line1` directly (coarse containers *and*, where refined, the inner spans within them), so a preview click is just `closest('[data-line0]')` — nearest ancestor naturally wins over the coarser one further out. The editor side has no per-line DOM of its own; it reuses `edithl.js`'s existing one-`.cm-row`-per-source-line overlay purely as a paint target (a `.sync-hit` class), without changing `edithl.js` — and because edithl replaces every row on each input and resize, a `MutationObserver` on `.cm-lines` puts the class back. In the preview a text line gets an underline, an image or PDF embed a bar under it (`text-decoration` cannot paint under a replaced element), a coarse block a bottom rule. Rebuilt on every `renderPreviewNow()`; afterwards, while the editor has focus the underline is re-derived from the caret, otherwise it is dropped on both sides, since the same line numbers may no longer hold the same text. In `renderPreviewNow()` it must run *before* `MD.resolveImages()`: splitting a paragraph or list item rewrites its `innerHTML`, which replaces its `<img>` elements, and on a cache miss `resolveImages` sets `src` asynchronously — in the other order the `src` lands on the discarded element, so every image in a paragraph or list item is blank when a note is opened and only appears after the next keystroke re-renders from cache (images in tables and callouts are unaffected, which makes it look intermittent).

- **檔案管理 is also a small cloud drive: its own folder tree, independent of notes (`server/db.js` table `file_folders`, `images.folder_id`).** Deliberately a *separate* table from the notes' `folders`, not a fifth `area` — an area's whole reason to exist is note visibility rules (`permFor`, `novelUnlocked`, the `AREAS` union in `resolveArea`), none of which has anything to do with organising uploads, and folding file folders into that system would drag them into all of it for nothing. `file_folders` is the bare minimum: `id`/`owner_id`/`name`/`parent_id`, no `area`, no sharing (檔案管理 was already private-per-caller before this). `GET/POST /api/file-folders`, `PUT/DELETE /api/file-folders/:id` (`server/api.js` `listFileFolders`/`createFileFolder`/`updateFileFolder`/`deleteFileFolder`) mirror the notes-folder endpoints' shape one-for-one. **Uploading into a folder is additive, not a new upload path**: `POST /api/images` gained an optional `X-Folder-Id` header and `POST /api/uploads` (chunked start) an optional `folderId` body field, both resolved through `resolveFileFolder()` (an id that isn't the caller's own, or doesn't exist, quietly resolves to `null` — the drive root — rather than erroring, the same forgiving stance `resolveArea` does not take for notes because here there is no visibility rule being bypassed, just a display location); every *existing* caller (paste, drop, toolbar 檔案, the course-file uploader) omits it and keeps landing at the root exactly as before. Browsing is folder-scoped (`matches()`'s `folderScoped()` check: a file only shows if `img.folderId` equals the browsed folder) *unless* a search query or the note-filter is active, in which case scope is dropped entirely — searching or filtering by note means "find it no matter where it is," not "find it in the folder I happen to be looking at." Drag-and-drop speaks two channels at once on the same elements: `DRAG_MIME` (`application/x-strikenote-files`, a JSON array of file ids — the files version of `dashboard.js`'s own private MIME types) for dragging a card onto a folder tile or a breadcrumb crumb to move it, and the browser's native `Files` type for dragging real files in from the OS to upload into whatever tile or breadcrumb crumb they're dropped on (or the open grid background, which uploads into whichever folder is currently browsed) — `hasFiles`/`hasInternalDrag` tell the two apart on `dragover` so a tile's drop handler does the right thing either way. **A real regression this shipped with and smoke.js now guards against**: `images.folder_id` added a trailing bound parameter to `insertImagePending`/`insertImage`'s SQL, and `server/backup.js`'s two restore call sites (recreating a missing file's row) were not updated to pass it — every restore then failed outright with mysql2's "Malformed communication packet" (a bound-parameter-count mismatch), caught by `npm run smoke`'s backup-restore section before anyone else could hit it. Restore now passes `null` (drive root) for the parameter; **backup/restore does not yet carry a file's folder placement** — a restored file always lands at the top level, not wherever it was filed before the backup, which is a known, accepted gap rather than something backup.js silently gets wrong.
- **Uploads are any file, and serving decides what a file may do.** `POST /api/images` takes any `Content-Type` (sanitised by `uploadMime`) plus the original name percent-encoded in `X-File-Name` (`images.name`). `server.js:sendUpload` serves only inert types as themselves — raster images, `application/pdf` (the in-note viewer needs it inline), SVG under a `sandbox` CSP — and everything else as an `application/octet-stream` attachment with `Content-Disposition` and `sandbox`. Keep it that way for every route that returns stored bytes (`/original` too): served under its claimed type, an uploaded `.js` satisfies `script-src 'self'` and an uploaded page runs in the app's origin. In notes: `![alt](img:<id>)` embeds an image, `![名稱](pdf:<id>)` embeds a PDF viewer, `[名稱](pdf:<id>)` shows the same PDF as a file link, `[名稱](file:<id>)` is any other attachment (`fileChipHTML` in `markdown.js`, via marked's `link` renderer, which returns `false` for ordinary links). Visibility and the library's "used" check (`getImage`, `MEDIA_REF`, `notesEmbeddingMedia`) know all three schemes; a new scheme must be added to all of them or its files 404 for share recipients and show as unused. Every upload path — paste, drop, toolbar 檔案, `/file`, and the library's own 上傳檔案 — goes through `uploadFiles` in `app.js`. The sidebar entry and dialog are 檔案管理 (`imagelib.js`, still `ImageLib`, still `/api/images`).
- **Big files are chunked end to end (`image_chunks`, `POST /api/uploads` → `PUT /api/uploads/:id/:seq` → `POST …/finish`).** One request is capped by `MAX_BODY_BYTES`, one MariaDB packet by `max_allowed_packet` (64M) and one request through Cloudflare by 100 MB, so a lecture video cannot go through `POST /api/images`. `Store.uploadFile(file, onProgress, mime)` sends anything over 20 MB (or anything the direct path refuses — the browser sees a status-less "Failed to fetch", not a 413, when the server hangs up mid-body) as `UPLOAD_CHUNK`-sized pieces (8 MiB, never more than `MAX_BODY_BYTES`; the server names the size, the client never assumes it), in order, one at a time. Each piece is its own `image_chunks(image_id, seq, data)` row; the `images` row carries `size`/`chunk_size` with an empty `data`, and stays `pending = 1` — invisible to `getImage`, the library, storage totals and backup — until `finishUpload` has counted every byte. `putChunk` insists on the exact expected length, acknowledges a repeat of a chunk it already holds (`seq < have` → `{next}`) instead of appending twice, and answers a chunk ahead of its turn with 409 + `next`, which is how a client that lost a reply resumes (`send()` in `server.js` passes `next` through on an error body for exactly this). Abandoned pending rows are swept hourly (`sweepPendingUploads`, from `purgeTrash`). **Serving** (`server.js:sendChunked`) streams the rows one at a time with back-pressure and honours a single `Range` (206 / 416, `Accept-Ranges: bytes`) — that is what makes a `<video>` seekable and lets Chrome find an MP4's trailing `moov`; type handling is the same `uploadHeaders()` as small files, so a chunked `.html` is still an `octet-stream` attachment under `sandbox`, and only `video/(mp4|webm|ogg)` and the listed `audio/*` types were added to `INLINE_UPLOAD`. A chunked file cannot be annotated (`saveImage` refuses, `/meta` says `canAnnotate: false`): annotation rewrites `images.data`, which serving would ignore. **Backup**: `ZipWriter.addStream()` writes a stored entry from an async source in two passes (CRC first, since the local header needs it) and `ZipReader.stream()` reads an entry piecewise verifying size + CRC at the end; `files.json` marks such entries `chunked: true` and restore re-chunks them into a pending row that is only finished — or deleted — at the end, so a broken archive never leaves a half file.

- **The images in an imported .md come with it (`js/mdimport.js`, shared by the browser and `server/tools/import-md.js`).** A `.md` from outside references pictures in three ways the site cannot use as they are — a relative path (`![](images/x.png)`: no such file on the site), an external URL (the CSP allows same-origin images only) and `<img src>` (never goes through the image renderer) — plus inline `data:` base64, which would otherwise sit in the note body as tens of KB of noise. `MdImport.scan(text)` returns every reference (`{target, kind: local|remote|data|other, alt, embed, start, end, syntax: link|refdef|html}`) and `MdImport.rewrite(text, resolve)` swaps in the site's own form (`![名稱](img:<id>)` / `![名稱](pdf:<id>)` / `[名稱](file:<id>)`, via `siteRef`) for whatever `resolve` returns an id for — **anything it returns `null` for is left exactly as it was**, which is what makes a missing file or an unfetchable URL a degraded import rather than a broken one. Three parsing details are load-bearing: fenced and indented code is excluded (`codeLines`), so a tutorial that *shows* `![x](images/cover.png)` keeps showing it; reference definitions (`[s1]: guide/img/step 1.png`) take the rest of the line minus a trailing title rather than stopping at the first space, because exported files routinely have spaces in filenames; and a destination with a raw space inside `()` — which marked itself does not accept as a link — is picked up by a second, looser pass (`LOOSE`) that only fires when the path resolves to a file actually in the import, turning an already-broken reference into a working image instead of risking a false positive. The two callers differ in exactly one way, and deliberately: the CLI downloads external images itself (on the user's own machine — **the server must never fetch a user-supplied URL**, see `linkpreview.js` for what that costs when it has to), while the browser leaves them as links and says so in the toast. Everything else is shared, so both surfaces upload one picture once however many notes reference it (`usedAssets`/`wantLocal`), resolve `./`, `../` and `%20` through `resolvePath`, take the note title from YAML front matter or the first heading (`frontMatter`, which also strips the YAML), and only import files nothing references when the target is 課程筆記, where they become ordinary `meta.file` file notes. In `app.js` the phases must stay in this order and inside the scan's `.then` — read+scan every file, *then* upload the referenced assets, *then* create the notes: building the upload/create chain outside that callback silently produced zero notes, because `usedAssets` and `docs` were still empty when `forEach` ran over them.
- **Link preview cards (`{%preview https://… %}`, `server/linkpreview.js`):** a block extension (`linkCardExtension`) renders only a frame with the address; `MD.resolveLinkCards` (called from `resolveImages`, and awaited by `inlineImagesAsDataURL` for PDF/book, which also inlines the thumbnail) fills title/description/image from `GET /api/link-preview`, with `textContent` only.
